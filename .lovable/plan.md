## Проблема

Когда в фильтре по браузеру/ОС/устройству выбрано `other`, `expandFilter()` возвращает `null` и мы **вообще не отправляем фильтр** для этой размерности на backend. Затем в `useEffect` пост-фильтрация выполняется только если текущая группировка совпадает с размерностью фильтра (например, `group_by=browser`). Во всех остальных группировках (страны, даты, siteid и т.д.) статистика возвращается без учёта выбранного `other` — видны все браузеры.

Backend принимает только «белый список» точных значений и не поддерживает исключения, поэтому нельзя просто отправить «всё кроме известных».

## Решение — двухшаговый запрос

Когда среди применённых фильтров есть `other` хотя бы по одной размерности (browser/os/device_type), в `useEffect` перед основным запросом делаем **предварительный запрос** к `api.statsQuery`, чтобы узнать какие «сырые» значения фактически присутствуют в данных для этих размерностей.

Алгоритм:

1. Собрать список размерностей с `other`: `otherDims = [{key:"browser", filterSet, map, filterField:"browser"}, ...]`.
2. Если `otherDims` пуст — работать как сейчас.
3. Иначе для каждой такой размерности выполнить лёгкий запрос:
   - те же `from/to/campaign_ids/creative_ids`
   - `group_by = <эта размерность>`
   - `filters` — все **остальные** уже раскрытые фильтры (для фильтров с `other` тоже пропускаем, как раньше)
   - взять `Object.keys(res.rows)` = сырые значения, присутствующие в выборке
4. Для каждой размерности с `other` вычислить итоговый список raw-значений:
   - взять сырые значения из шага 3
   - оставить только те, чья группа (через `mapRawToGroup`) входит в `filterSet` (это автоматически включит `other` = unknown, и любые дополнительно выбранные известные группы)
   - подставить этот список в `filters[<field>]` основного запроса
5. Выполнить основной запрос как обычно.
6. Пост-фильтрацию при `group_by == этой же размерности` оставить — она уже работает корректно.

Запросы шага 3 для разных размерностей можно запускать параллельно через `Promise.all`.

## Побочные эффекты

- Одна дополнительная сетевая поездка (или до трёх параллельных), только когда пользователь реально выбрал `other`. В остальных случаях поведение не меняется.
- Overlay «загрузка» продолжает работать (таймер 1с покрывает оба шага).
- `cancelled`-флаг проверяем и после предварительного запроса, чтобы не гонять устаревшие ответы.
